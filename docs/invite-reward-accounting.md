# 邀请奖励来源与结算

新转换的邀请奖励仍计入可用总余额，同时在 `users.reward_balance` 记录其中的奖励部分（包括 Redis 已授权但未消费的额度），不是额外增加一笔余额。消费优先使用奖励部分，这部分不再产生上级返佣；剩余消费沿用原有返佣规则及个人/系统比例。退款按原来源恢复，先退普通资金，再退奖励，专属模型积分保持原有逻辑。

`invite_rebates` 按用户和请求 corr_id 唯一记录资金来源、非奖励净消费、邀请人及比例快照、已发奖励。在扣费流水的数据库事务内同步更新；失败一起回滚。后台任务只在 LLM 日志成功或异步任务成功后结算，存在未完成退款补偿任务时等待。预扣、处理中和失败请求不会提前产生可转换奖励。按请求净额计算，而非对 hold/settle/refund 分别取整。并发任务在行锁内按目标奖励与已发奖励差额更新，防止重复发放。

已发奖励若遇到后续退款，先扣冻结奖励。不足部分记入 `users.rebate_debt`，以后的邀请收益优先抵扣，不再因冻结余额不足而丢失回扣。它不是扣减用户充值余额，也不能立即追回已经提现或消费掉的奖励。

## 升级边界

- 服务启动时 Sync2 新增两个用户字段和 `invite_rebates` 表。先停止接入新请求，等待旧版在途请求、退款及返佣任务处理完成，再停止旧实例并启动新版完成迁移；勿让新旧版本同时写账。
- 升级前已经转换到普通余额的奖励缺少转换流水，不能可靠重建来源；原余额保留，奖励来源追踪从新版转换开始。仍在冻结余额中的历史奖励，在新版转换后也会标记为奖励。
- 旧版尚未完成的返佣任务保留兼容处理；没有新来源记录的历史退款走旧任务回扣，并保留不足部分的欠扣记录。上线前仍应按上一条排空旧在途请求，避免跨版本结算。
- 不扫描或追扣已经结束的历史账单，不改邀请绑定、防环或七天绑定窗口。

本地回归：`go test ./... -count=1`。PostgreSQL 事务、并发发放和回扣测试需设置指向测试数据库的 `FANAPI_TEST_DATABASE_URL`，测试创建并清理独立 schema。
