# LLM 错误摘要与号池轮转修复设计

## 目标

消除新 LLM 调用日志中残留的原始错误响应正文，并确保同一号池轮转到不同 `base_url_override` 时，请求格式始终与该 Key 的有效上游协议一致。

## 范围

- HTTP/SSE 与 Responses WebSocket 的非成功上游响应不再把原始 body 写入 `llm_logs.error_msg`。
- 错误日志只保留可读摘要：优先使用已识别的业务错误消息；无法识别时只记录 HTTP 状态；任何摘要最多 4 KiB。
- 读取上游错误体设置有限上限，避免异常代理返回无限大 body 时占用请求内存。
- 初始号池 Key 与每次 Key 轮转都从同一份原始客户端请求重新生成：有效 URL、协议、自动转换、请求脚本、Claude 补全和 OpenAI 流式 usage 注入。

## 非目标

- 不修改数据库表结构、索引或历史日志。
- 不改变正常成功响应、计费、退款或渠道级重试的语义。
- 不禁止号池内不同 Key 使用不同上游 URL；它们继续受现有 URL 校验约束。

## 设计

### 错误日志

新增一个 handler 内部的错误摘要边界：有结构化 JSON 时复用现有通用错误识别，保留其 `message`；无结构化错误时只保存 `上游返回 <status>`。所有写入日志的错误文本都经过统一的 UTF-8 安全 4 KiB 截断，以防其他路径再次传入过大字符串。错误响应读取通过有界 reader 完成，业务错误识别仍在上限范围内执行。

### 号池轮转

新增“按当前 PoolKey 准备上游尝试”的小函数。它以原始客户端格式请求为输入，针对当前 Key 的覆盖 URL 解析目标 URL 和协议，再依次完成协议转换、请求脚本和协议特有补全。首次请求与每次 `401/403/429/504/521` Key 轮转都调用此函数，不能继续复用前一把 Key 的 `mappedReq` 或 `proto`。

## 验收

1. 超大或 HTML 错误响应不会原样出现在 `LLMLog.ErrorMsg`，长度不超过 4 KiB。
2. JSON 错误的标准 `error.message` 仍可作为可读摘要保留。
3. 从固定 Responses URL 轮转到 `/v1` Chat URL（以及反向场景）时，每次尝试使用对应协议和请求格式。
4. 既有 `/v1` 路由、Responses Compact、请求脚本、passthrough、流式 usage 与全量 Go 测试保持通过。
