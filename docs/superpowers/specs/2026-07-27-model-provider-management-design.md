# 模型企业管理设计

## 决策状态

本设计新增独立模型企业管理能力，并取代
`2026-07-27-model-group-provider-hierarchy-design.md` 中“企业仅保存为规范化字符串、不建立企业表”的旧决策。
原有三级业务结构、API Key 跨企业绑定和企业内独立排序保持不变：

```text
模型企业 -> 模型分组 -> 对外模型 -> 后台渠道
```

## 目标

- 管理员可以新增、编辑、排序、启用和停用模型企业。
- 模型分组和渠道只能从企业下拉框选择，不再自由填写企业名称。
- 企业编码和显示名称均大小写不敏感地唯一，彻底避免 `openai`、`Openai`、`OpenAI` 被识别为多个企业。
- 企业停用后，该企业下所有分组、模型和渠道立即停止参与新请求路由。
- 一个 API Key 仍可绑定多个企业下的多个分组，企业内分组顺序仍独立生效。
- 客户端仍只提交 API Key 和精确 `model`，不新增企业参数。
- 已被分组或渠道引用的企业禁止物理删除；完全未被引用的企业允许删除。
- 继续使用现有管理员账户和管理员鉴权，不新增运营角色或企业级权限体系。

## 非目标

- 不增加企业级计费、配额、密钥池或租户隔离。
- 不允许客户端指定企业绕过服务端模型归属判断。
- 不根据模型名称前缀猜测企业。
- 不在停用企业时批量修改其分组、渠道或 API Key 绑定。
- 不为低基数企业数据新增缓存；路由直接通过现有单次关联查询判断状态。

## 数据模型

### `model_providers`

新增表：

```text
id          bigint primary key
code        varchar(64) not null
name        varchar(128) not null
is_active   boolean not null default true
sort_order  integer not null default 0
created_at  timestamp
updated_at  timestamp
```

约束：

- `code` 保存小写稳定标识，只允许 `[a-z0-9][a-z0-9_-]*`。
- `LOWER(code)` 唯一。
- `LOWER(BTRIM(name))` 唯一。
- `name` 去除首尾空格后不得为空。
- 被分组或渠道引用时，数据库外键和服务层同时阻止删除。
- 企业被引用后 `code` 不可修改；`name`、`sort_order` 和 `is_active` 可以修改。

### 分组和渠道关联

向 `model_groups` 和 `channels` 增加：

```text
model_provider_id bigint references model_providers(id)
```

迁移完成后两个字段均为非空，企业 ID 是唯一事实来源。现有字符串字段 `model_provider`
仅在兼容迁移期保留：旧接口读取时可以继续返回 `model_provider`，但值由关联企业的 `name`
生成；新写入必须解析为企业 ID，路由和校验不得再依赖字符串字段。后续独立迁移再删除旧数据库列。

模型分组与渠道的企业必须一致。绑定渠道到分组、修改分组企业或修改渠道企业时，都在事务中校验已有模型绑定，失败时不写入部分数据。

### API 兼容字段

- 管理端新建或修改分组、渠道时必须提交 `model_provider_id`，不再接受企业名称作为新写入依据。
- 分组和渠道响应继续返回兼容字段 `model_provider`，其值来自关联企业的 `name`。
- 响应同时返回 `model_provider_id`，并在需要排序或诊断的列表中返回企业的 `is_active` 和 `sort_order`。
- API Key 的 `group_ids` 请求格式不变；用户可见分组摘要携带上述企业字段，前端不单独维护企业副本。

## 管理接口

新增管理员接口：

```text
GET    /api/admin/model-providers?include_inactive=true
POST   /api/admin/model-providers
PUT    /api/admin/model-providers/:id
PATCH  /api/admin/model-providers/:id/toggle
DELETE /api/admin/model-providers/:id
```

列表响应包含企业基本信息及 `group_count`、`channel_count`，用于停用确认和删除保护提示。

创建规则：

- 规范化并校验 `code`、`name`。
- 编码或名称大小写不敏感重复时返回 `409`。
- 新企业默认启用，排序值可由管理员填写；未填写时排在现有企业之后。

更新规则：

- 未被引用时可以修改编码。
- 被任一分组或渠道引用后，修改编码返回 `409`。
- 修改显示名称不会改变路由关系。

删除规则：

- `group_count` 或 `channel_count` 大于零时返回 `409`，并返回两个引用数量。
- 两个引用数量均为零时允许物理删除。

## 管理端界面

### 模型企业页面

管理员导航新增“模型企业”页面，使用紧凑表格展示：

- 显示名称、企业编码、分组数、渠道数、排序、状态和操作。
- 支持新增、编辑、启用、停用和删除。
- 停用确认框展示受影响的分组数和渠道数，并明确说明新请求会立即停止使用该企业。
- 删除按钮仅在无引用时可执行；有引用时保留禁用状态和原因提示。
- 排序使用数值输入或现有轻量排序模式，不引入拖拽依赖。

### 模型分组和渠道页面

- 原自由输入或 datalist 改为企业下拉框。
- 新建记录只能选择启用企业。
- 修改企业时只能选择启用企业。
- 编辑属于停用企业的历史记录时仍显示当前企业，并允许保存与企业无关的字段；不能新绑定模型或切换到另一个停用企业。
- 企业停用状态在下拉框和列表徽标中清晰显示。
- 企业列表按 `sort_order, id` 排序。

### API Key 页面

- 企业标签按企业的 `sort_order, id` 排序，而不是按首次出现顺序。
- 只展示启用企业下可供新绑定的启用分组。
- 编辑已有 API Key 时，停用企业和其已有绑定以只读诊断状态显示，保存时不得静默删除这些绑定。
- 企业重新启用后，原有分组选择和企业内顺序恢复可编辑，无需重建 API Key 绑定。

API Key 分组替换接口必须在服务端比较现有绑定和请求值。停用企业下的既有绑定只能原样保留，不能通过替换请求新增、删除或重排；不满足时返回 `400`。这条约束不能只依赖前端只读状态。

## 停用语义与请求路由

停用企业只更新 `model_providers.is_active=false`，不修改子记录。现有候选路由查询增加企业关联和启用条件：

```sql
JOIN model_providers mp ON mp.id = model_groups.model_provider_id
WHERE mp.is_active = TRUE
  AND model_groups.is_active = TRUE
  AND channels.is_active = TRUE
```

因此停用提交成功后的下一次请求立即停止使用该企业。普通 HTTP、SSE、任务代理、Responses WebSocket、Realtime WebSocket 和显式 `channel_id` 授权必须共享该条件，不能存在绕过入口。

企业重新启用后，既有分组、模型、渠道和 API Key 绑定自动恢复参与路由，仍受各自启用状态、协议、健康过滤和重试规则约束。

若企业停用导致 Key 对目标模型不再有候选路由，沿用现有“API Key 分组中没有可用模型”错误，不回退到其他企业或全局渠道。

## 一致性和并发

- 企业唯一性由数据库大小写不敏感唯一索引兜底，不能只依赖应用层查询。
- 分组/渠道企业修改和已有绑定校验在同一事务中执行。
- 删除使用外键 `RESTRICT` 作为最终保护，即使引用数量预检后发生并发写入也不会误删。
- 路由查询每次读取企业启用状态，不使用可能延迟失效的进程缓存。
- 企业停用不锁定或重写 API Key 绑定，避免大范围写放大。

## 历史数据迁移

迁移必须显式执行，不在服务启动时自动连接或修复生产数据库。

1. 创建 `model_providers`，给分组和渠道增加可空 `model_provider_id`。
2. 汇总 `model_groups.model_provider` 与 `channels.model_provider`，按 `LOWER(BTRIM(value))` 归并候选企业。
3. 常用企业使用确定映射生成编码，例如 `OpenAI -> openai`、`Anthropic -> anthropic`。
4. 自定义企业编码由规范化名称生成；若不同名称生成相同编码、名称为空或无法生成合法编码，审计失败并要求人工指定，不自动猜测。
5. 回填分组和渠道的 `model_provider_id`。
6. 审计空引用、无效引用、分组/渠道企业不一致、跨企业同名 `routing_model` 和编码/名称冲突。
7. 只有所有审计计数为零时，才启用非空约束、唯一索引和外键验证。
8. 部署新代码后保留旧字符串列一个兼容周期；确认所有读写均使用企业 ID 后，再用独立迁移删除旧列。

迁移失败不得更新迁移账本，也不得仅因为部分回填成功就手工标记完成。

## 错误处理

- 企业编码或名称重复：`409 Conflict`。
- 企业不存在或已删除：`404 Not Found`。
- 新建分组/渠道选择停用企业：`400 Bad Request`。
- 修改记录到停用企业：`400 Bad Request`。
- 删除被引用企业：`409 Conflict`，返回引用数量。
- 修改已被引用企业的编码：`409 Conflict`。
- 企业停用后的模型调用：沿用现有模型不可用错误。
- 数据库查询失败：返回内部错误，不降级到未授权渠道。

## 测试与验收

### 后端

- 企业编码和名称大小写不敏感唯一。
- 企业编码格式、空名称和排序校验。
- 未引用企业允许删除，被分组或渠道引用时拒绝删除。
- 被引用企业禁止修改编码，允许修改名称。
- 停用企业立即从普通、流式、任务、WebSocket 和显式渠道授权候选中排除。
- 重新启用企业恢复原绑定路由。
- 分组和渠道企业不一致时拒绝绑定或修改，并保持事务原子性。
- 单次候选查询继续保持企业内分组顺序、健康过滤和重试行为。
- 迁移审计能识别空值、冲突、自定义编码碰撞和跨企业同名模型。

### 前端

- 企业页面新增、编辑、排序、启用、停用和引用保护。
- 停用确认展示影响范围。
- 分组和渠道表单使用同一企业下拉数据源。
- 新建记录不显示停用企业；编辑历史记录保留停用企业诊断状态。
- API Key 创建和编辑按企业排序，跨企业选择和企业内排序不变。
- 停用企业已有绑定不会在保存时被静默删除。
- 桌面和 390px 移动端无溢出、遮挡或不可见操作。
