# API Key 删除与吊销即时失效设计

## 背景

FanAPI 当前将有效 API Key 的完整记录缓存到 Redis，缓存期限为 30 分钟。鉴权命中缓存后直接放行；用户删除和管理员吊销只修改数据库，没有同步删除 `apikey2:{key_hash}`。因此，已经进入缓存的 Key 在删除或吊销后仍可能继续使用。

OctoAPI 当前主鉴权链已经在删除、吊销数据库记录后删除对应 Redis 缓存，并由新的 `authn.Service` 执行鉴权，本次不修改 OctoAPI。

## 目标

- 用户删除 API Key 后，删除提交完成后的新请求立即鉴权失败。
- 管理员吊销 API Key 后，吊销提交完成后的新请求立即鉴权失败。
- Redis 缓存删除偶发失败时，数据库状态仍能阻止缓存中的旧记录被放行。
- 保留现有数据库结构、API 路径和 30 分钟正常缓存期限。

## 方案

在 `internal/service/auth.go` 集中定义 API Key 缓存键生成与失效操作，删除和吊销入口不再自行拼接缓存键。

用户删除与管理员吊销按以下顺序执行：

1. 在数据库中按请求权限范围读取目标 Key 的 `key_hash`。
2. 执行删除或将 `is_active` 更新为 `false`。
3. 删除 Redis 中对应的 `apikey2:{key_hash}`。
4. 缓存删除失败时返回服务端错误，不把操作报告为完全成功。

鉴权命中 Redis 后，使用现有的 `last_used_at` 数据库更新同时附加 `is_active = true` 条件，并检查受影响行数。记录已删除或已吊销时拒绝鉴权，不返回缓存对象。这样即使步骤 3 因瞬时 Redis 故障未完成，数据库仍是最终权威。

## 一致性边界

- “立即失效”指删除或吊销数据库变更完成之后发起的新 HTTP 或 WebSocket 握手请求。
- 已经通过鉴权并建立的请求或 WebSocket 连接不会被主动中断；这需要独立的连接注册与广播机制，不属于本次范围。
- 数据库变更成功但 Redis 删除失败时，接口返回错误；重复删除可能得到不存在响应，但旧 Key 仍会被鉴权阶段的数据库复核拒绝。
- 不新增表、字段、迁移或外部依赖。

## 错误处理

- 目标 Key 不存在或不属于当前用户时，用户删除接口保持 `404`。
- 管理员吊销无效 ID 或不存在的 Key 时应返回相应客户端错误，不再无条件报告成功。
- 数据库读取、变更或 Redis 删除失败时返回 `500`，日志和响应不得包含原始 API Key。

## 测试

- 缓存键生成和失效使用统一逻辑。
- 用户删除成功后，对应缓存被删除。
- 管理员吊销成功后，对应缓存被删除。
- 缓存中仍有旧记录但数据库记录已删除或已吊销时，`LookupAPIKey` 拒绝该 Key。
- 删除或吊销未命中目标记录时，不误删其他 Key 的缓存。
- 运行相关 Go 测试、`go test ./... -count=1` 和 `git diff --check`。
