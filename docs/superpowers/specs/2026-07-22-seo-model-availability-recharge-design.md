# FanAPI SEO、模型可用性与充值套餐设计

## 背景与目标

FanAPI 是独立平台，不引入租户概念。本次改动完成三件事：

1. 增加平台级 SEO 标题和描述，并让配置真正作用于浏览器页面元信息。
2. 在现有用户模型列表的每张模型卡片中展示该模型独立的真实调用可用性。
3. 验证并保护现有充值套餐链路，不改变充值、赠送积分和历史账务行为。

## 非目标

- 不增加租户、站点隔离或按域名切换设置。
- 不主动探测模型，不制造上游请求或额外账单。
- 不增加独立状态页，不改变模型列表入口。
- 不重构充值套餐数据结构，不修改历史订单、余额或账本。
- 不根据主观延迟阈值生成黄色记录；最近调用只展示成功或失败。

## 平台 SEO

沿用 `system_settings` 键值配置，不新增数据表或迁移。新增公开键：

- `seo_title`
- `seo_description`

管理员在现有平台设置页面编辑这两个字段。`GET /public/settings` 公开返回它们。前端站点设置模型增加对应字段，并在设置加载完成后执行以下规则：

- `document.title` 优先使用非空 `seo_title`，否则回退到 `site_name`。
- 将非空 `seo_description` 写入唯一的 `<meta name="description">`。
- 配置为空时移除旧的 description 标签，避免热更新或测试环境残留旧值。
- SEO 配置加载失败时继续使用现有站点名回退，不阻断页面。

## 模型可用性 API

新增登录用户批量接口：

```text
GET /user/model-availability
```

接口以当前用户可见的模型列表为边界，只返回当前启用模型分组中可见的 `routing_model`，不能通过统计接口枚举未授权模型。

返回结构：

```json
{
  "models": [
    {
      "routing_model": "gpt-5.6-sol",
      "total": 1284,
      "success": 1279,
      "availability_percent": 99.61,
      "p50_latency_ms": 2850,
      "recent": [
        { "status": "ok", "latency_ms": 2410, "created_at": "2026-07-22T10:00:00Z" }
      ]
    }
  ]
}
```

### 聚合口径

- 时间范围固定为最近 7 天。
- 聚合键是用户模型列表展示的 `routing_model`。
- 数据来源是实际 `llm_logs`，通过请求记录的 `model` 与关联 `channel_id` 约束到当前可见模型，避免把其他别名错误归入同一模型。
- `status = 'ok'` 计为成功；其他已经结束的状态计为失败；`pending` 不进入成功率分母。
- P50 只统计成功请求的 `updated_at - created_at`。
- `recent` 最多返回每个模型最近 60 条已结束记录，并按时间正序输出，供前端从过去到现在绘图。
- 模型没有有效日志时仍由前端与模型列表合并并展示“暂无调用数据”。

接口与 `/user/channels` 并行加载，避免每张卡片分别查询产生 N+1。查询必须使用参数化 SQL，并复用现有 `llm_logs(model, created_at)`、`llm_logs(channel_id, created_at)` 索引；实现后以 `EXPLAIN` 或集成测试确认不做无界全表扫描。除非验证表明现有索引不足，否则不新增迁移。

## 模型卡片

保留现有模型卡片中的名称、供应商、协议、计费方式、价格、描述和模型 ID。在卡片底部增加一个独立可用性区域：

- 近 7 天可用率；
- 成功请求 P50 耗时；
- 近 7 天有效请求数；
- 最近 60 次请求的小柱图。

状态规则：

- 有效请求少于 20：`数据较少`；
- 至少 20 次且可用率大于等于 99%：`正常`；
- 至少 20 次且可用率大于等于 95%、小于 99%：`降级`；
- 至少 20 次且可用率小于 95%：`异常`；
- 零请求：`暂无调用数据`。

柱图使用绿色表示成功、红色表示失败，并同时提供文本或可访问标签，不能只依赖颜色。悬停信息包含请求时间、结果和耗时。统计接口失败时，模型与价格继续展示，仅可用性区域显示“统计暂不可用”。

桌面端维持现有响应式卡片网格；如果新增内容使四列卡片无法保持可读性，应在相应宽度减少列数。移动端单列显示，模型 ID、价格和统计文字不得溢出或遮挡。

## 充值套餐现状与保护范围

现有链路保持不变：

1. 管理员通过 `AdminSettingsPage` 保存 `recharge_plans` 和 `recharge_allow_custom`。
2. `GET /public/settings` 向用户端下发公开套餐。
3. `UserBillingPage` 展示套餐并提交支付金额。
4. `CreateEpayOrder`、`CreatePayApplyOrder`、`CreateShouqianbaOrder` 都调用 `planCredits()`。
5. `planCredits()` 对匹配套餐发放基础积分与赠送积分，不匹配时维持现有自定义金额换算规则。

本次不改变 `recharge_allow_custom` 的既有服务端语义，也不追溯调整历史充值。增加回归测试确保三个支付入口继续调用同一套餐积分计算，并验证套餐金额匹配、赠送积分和普通金额换算。

## 错误处理与安全

- 可用性统计只暴露汇总结果，不返回用户、API Key、错误正文、请求体或响应体。
- 单个模型无日志不是错误。
- 统计查询失败不影响模型列表和调用文档。
- SEO 字段按普通文本处理，不接受或注入 HTML。
- 充值套餐测试不得调用真实支付上游。

## 验证

后端测试覆盖：

- 可用模型过滤与模型分组聚合；
- 成功率、P50、`pending` 排除和最近 60 条顺序；
- 未授权模型不出现在统计响应；
- 无日志模型和统计查询错误；
- 三个支付入口的套餐积分计算回归。

前端测试覆盖：

- SEO 标题、description 写入、回退和清理；
- 模型统计正常、数据较少、无数据、异常和接口失败状态；
- 模型列表与统计接口并行加载且不产生逐卡请求；
- 充值套餐展示和选择契约。

最终运行聚焦 Go 测试、`go test ./... -count=1`、前端单元测试、构建和 `git diff --check`。使用浏览器检查桌面与移动端模型列表，确认图表非空、文字不重叠、卡片高度稳定。
