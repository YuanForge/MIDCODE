# 模型企业、分组与模型三级路由设计

## 背景

当前 API Key 可以绑定多个有序模型分组。请求根据 `routing_model` 逐个检查 Key 已绑定的分组，找到同名模型后按分组顺序请求和重试。该行为能够区分 GPT 与 Claude 模型，但模型分组没有明确的企业属性，用户选择分组时只能依赖名称判断；路由实现还会对每个绑定分组分别查询，产生随分组数量增长的数据库往返。

本设计在不改变标准模型请求格式的前提下，引入以下三级用户视图：

```text
模型企业 -> 模型分组 -> 对外模型
```

实际渠道是对外模型下的后台实现细节，不在 API Key 分组选择界面展示。

## 目标

- 一个模型分组只属于一个模型企业。
- 一个 API Key 可以同时绑定多个企业下的多个分组。
- 用户创建 API Key 或调整分组时，可以按企业识别、选择和排序分组。
- 每个企业内的分组拥有独立的相对请求和重试顺序。
- 用户请求仍只提交 API Key 和 `model`，不增加企业参数。
- 后端使用一次关联查询获得当前 Key、当前模型的候选分组和渠道，替代逐组查询。
- 保持现有健康渠道优先、全不健康时回退全部授权候选以及失败重试行为。

## 非目标

- 不新增模型企业管理表、企业级权限或企业级计费规则。
- 不要求客户端根据企业调用不同接口。
- 不根据 `gpt-*`、`claude-*` 等前缀强制猜测请求企业。
- 不在首版增加新的路由缓存；先用一次有索引支持的关联查询消除 N+1 查询。
- 不改变 API Key 对模型分组的授权边界，也不允许跨企业替换为不同模型。

## 业务规则

1. `model_groups` 的每条记录必须有且只有一个 `model_provider`。
2. 一个 API Key 可以绑定 OpenAI、Anthropic、Google 或自定义企业下的任意多个启用分组。
3. 分组排序只在同一企业内有业务含义。不同企业之间不存在请求先后关系。
4. 同一 `routing_model` 可以存在于同一企业的多个分组中，并分别映射到不同渠道和价格。
5. 同一 `routing_model` 不能同时归属于不同企业。请求不携带企业参数，因此跨企业同名会造成歧义。
6. 分组内绑定渠道的 `EffectiveModelProvider` 必须与分组企业大小写不敏感地一致。
7. 请求只使用精确 `routing_model` 匹配。未包含该模型的企业和分组不会成为候选。
8. 重试只在当前 Key 已绑定、企业一致且包含同一 `routing_model` 的分组之间进行。
9. Key 未绑定目标模型时返回模型不可用，不回退到其他企业的其他模型。

示例：

```text
API Key A
  OpenAI
    1. gpt-k12
    2. gpt-plus
  Anthropic
    1. claude
    2. claude-k12
```

`model=gpt-4.1` 只使用 OpenAI 下包含 `gpt-4.1` 的已绑定分组；`model=claude-sonnet-4` 只使用 Anthropic 下包含该模型的已绑定分组。

## 数据模型

### `model_groups.model_provider`

为 `model_groups` 增加：

- `model_provider varchar(128) not null`
- 去除首尾空格后不能为空。
- API 字段名保持为 `model_provider`。

首版不创建独立企业表。常用企业由界面提供建议选项，自定义企业仍保存为规范化字符串。

### 企业名称规范化

服务层提供一个共享规范化函数，创建或更新分组时统一调用：

- 去除首尾空格并合并多余内部空格。
- 常用企业按大小写不敏感方式映射为规范名称，例如 `openai` -> `OpenAI`、`anthropic` -> `Anthropic`。
- 自定义企业按大小写不敏感方式复用数据库中已有的显示名称，避免生成仅大小写不同的标签。
- 空值返回校验错误。

企业字段不是协议字段。OpenAI 兼容协议渠道仍应按其模型所属企业填写，例如 Claude 模型仍属于 Anthropic。

## 管理端约束

### 分组创建与编辑

- 分组表单增加必填“模型企业”。
- 输入控件提供 OpenAI、Anthropic、Google、DeepSeek、Alibaba 等常用选项，并允许输入自定义企业。
- 修改已有分组企业前，校验分组内所有绑定渠道；只要存在企业不一致就拒绝更新，并返回冲突模型和渠道。
- 分组列表增加企业标签，支持按企业快速识别。

### 模型绑定

绑定模型到分组时依次校验：

1. 分组和渠道均存在且启用。
2. `routing_model` 与渠道的 `ChannelRoutingKey` 一致。
3. 渠道的 `EffectiveModelProvider` 非空且与分组企业一致。
4. 其他企业的启用分组中不存在相同 `routing_model`。

同企业不同分组中的同名模型继续允许。修改分组企业和新增模型绑定使用事务内校验，避免保存一半配置。

## API Key 选择与排序界面

创建 API Key 和“调整模型分组顺序”复用同一选择组件，并参考用户提供的企业切换式 UI：

- 弹窗顶部使用企业切换栏，展示企业名称和已选分组数量。
- 切换栏下只展示当前企业的可选分组。
- 分组项展示名称、企业标签、模型数量以及现有价格或说明信息。
- 当前企业下方展示已选分组的重试顺序。
- 上下移动按钮只调整当前企业内的分组。
- 切换企业时保留其他企业的选择和顺序。
- 未选择任何分组的企业不参与该 Key 的路由。
- 移动端企业切换栏横向滚动，分组项和顺序列表使用单列布局。

后端接口继续接收一个有序 `group_ids` 数组，不增加嵌套企业结构。前端按稳定的企业显示顺序展开各企业列表；后端继续将其规范化为连续的全局 `priority`。运行时只比较同一模型的候选，因此不同企业之间的全局序号不影响企业内相对顺序。

API Key 列表和分组绑定接口返回的分组摘要增加 `model_provider`，用于恢复企业分区、勾选状态和企业内顺序。

## 请求路由

客户端请求格式保持不变：

```json
{
  "model": "gpt-k12"
}
```

路由器使用 API Key ID 和精确 `routing_model` 一次查询候选：

```sql
SELECT api_key_model_groups.priority,
       api_key_model_groups.id AS binding_id,
       model_groups.id AS group_id,
       model_groups.model_provider,
       channels.*
FROM api_key_model_groups
JOIN model_groups
  ON model_groups.id = api_key_model_groups.group_id
JOIN model_group_models
  ON model_group_models.group_id = model_groups.id
JOIN channels
  ON channels.id = model_group_models.channel_id
WHERE api_key_model_groups.api_key_id = ?
  AND model_group_models.routing_model = ?
  AND model_groups.is_active = true
  AND channels.is_active = true
ORDER BY api_key_model_groups.priority ASC,
         api_key_model_groups.id ASC;
```

需要指定协议的入口继续附加有效协议过滤。显式 `channel_id` 授权也改为等价的关联存在性查询，不能绕过 Key、分组、模型和企业约束。

查询后的处理顺序保持：

1. 排除本次调用已尝试的渠道。
2. 优先保留 Redis 健康状态正常的授权候选。
3. 存在健康候选时只返回健康候选。
4. 所有授权候选均不健康时返回全部授权候选，维持现有可用性回退。
5. 按企业内分组相对顺序请求和重试。

HTTP/SSE、普通任务代理、Responses WebSocket、Realtime WebSocket 和显式渠道授权必须共用该候选选择语义。

现有 `(api_key_id, priority, id)` 与 `(group_id, routing_model)` 索引支持该关联路径。首版不为低基数企业字段增加索引；只有实际执行计划或监控证明需要时再补充。

## 错误处理

- 分组企业为空：`400`，提示模型企业必填。
- 渠道企业为空：`400`，提示先完善渠道的模型企业。
- 渠道与分组企业不一致：`400`，返回分组企业、渠道企业和冲突模型。
- 同一模型已属于其他企业：`400`，返回模型名和已有企业。
- 修改企业与已有绑定冲突：`400`，列出冲突模型，不修改数据库。
- Key 没有目标模型候选：继续返回现有模型不可用错误。
- 数据库查询失败：返回现有内部错误路径，不降级为未授权的全局渠道选择。

前端在当前弹窗内展示服务端错误，保留用户尚未保存的选择和顺序。

## 历史数据迁移

迁移必须显式执行，不在服务启动时自动猜测或修正生产分组。

1. 增加 `model_provider`，迁移阶段暂时允许空字符串。
2. 对每个分组聚合其已绑定渠道的 `model_provider`。
3. 所有渠道都有值且大小写不敏感地属于同一企业时，自动回填规范名称。
4. 渠道企业为空、同组出现多个企业或同名模型跨企业时，写入迁移审计结果并停止强约束启用。
5. 管理员先通过现有渠道管理界面补齐渠道企业，再用经过审阅的显式迁移 SQL 修正无模型分组或其他特殊分组的企业；该步骤不依赖尚未部署的新分组企业界面。
6. 重新执行只读审计，确认以下计数均为零：空企业分组、同组多企业、跨企业同名模型、空企业渠道绑定。
7. 审计通过后再启用非空约束并部署依赖企业字段的新代码。

不得仅因迁移脚本部分更新成功就手工标记迁移完成。生产执行前必须核对数据库身份、目标表结构、约束和审计结果。

## 测试与验收

### 后端

- 常用企业和自定义企业名称规范化。
- 空企业被拒绝。
- 同企业不同分组允许相同 `routing_model`。
- 不同企业拒绝相同 `routing_model`。
- 渠道企业与分组企业不一致时拒绝绑定。
- 修改分组企业时完整校验已有模型并保持事务原子性。
- 单次候选查询只返回当前 Key、当前模型、启用分组和启用渠道。
- 候选保持企业内分组顺序，并正确排除已尝试渠道和不匹配协议。
- 健康候选优先及全不健康回退行为不变。
- 显式 `channel_id` 不能绕过企业和分组授权。
- 历史数据审计分别识别可自动回填、空企业、多企业和跨企业同名情况。

### 前端

- 创建 Key 和调整顺序使用一致的企业切换组件。
- Key 可以同时选择多个企业的分组。
- 切换企业后勾选状态和顺序不丢失。
- 上下移动只影响当前企业。
- 保存的 `group_ids` 保持每个企业内部顺序。
- 重新打开已有 Key 时正确恢复企业分区和顺序。
- 企业名称、长分组名和模型数量不会导致弹窗溢出。
- 浏览器验证桌面和 390px 移动端布局、滚动、选中态、错误态和保存流程。
