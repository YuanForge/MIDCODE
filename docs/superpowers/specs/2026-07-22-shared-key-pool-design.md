# 渠道共享号池设计

## 1. 目标

将渠道与号池的关系调整为多渠道对单号池：

- 一个渠道最多绑定一个号池。
- 一个号池可以同时被多个渠道绑定。
- 未绑定号池的渠道继续使用渠道自身的静态认证配置。

本次不支持一个渠道绑定多个号池，不增加号池优先级、跨池轮转或跨池故障转移。

## 2. 当前问题

当前结构同时保存两条绑定信息：

- `channels.key_pool_id` 表示渠道使用的号池。
- `key_pools.channel_id` 表示号池归属的渠道。

运行时按 `channels.key_pool_id` 取号池，但管理端列表、号池创建、供应商上传和部分缓存重置逻辑依赖 `key_pools.channel_id`。`key_pools.channel_id` 还带有指向渠道的级联删除外键。直接让第二个渠道引用已有号池，会造成管理端归属错误、供应商校验错误，以及删除原渠道时误删共享号池的风险。

## 3. 权威数据模型

`channels.key_pool_id` 是唯一权威绑定：

```text
channels.key_pool_id -> key_pools.id
```

多个渠道允许保存相同的非零 `key_pool_id`。首版继续使用 `0` 表示未绑定，避免扩大 Go 模型、接口和现有数据的空值兼容范围。

保留 `key_pools.channel_id`，但改为可空的兼容字段，语义调整为“默认/测试渠道”，不再表示唯一绑定关系。真正的运行时绑定仍只认 `channels.key_pool_id`。号池可以为 NULL，或保留一个默认渠道 ID；多个渠道可以同时引用同一个号池。该字段不允许再使用级联删除，删除默认渠道时改为将其置 NULL。

不新增中间表。中间表只有在未来支持一个渠道绑定多个号池时才有必要。

## 4. 数据迁移

新增 `scripts/migrate_20260722_shared_key_pools.sql`，执行以下操作：

1. 检查所有非零 `channels.key_pool_id` 都指向存在的 `key_pools.id`；存在悬空引用时迁移必须失败并输出待修复记录。
2. 将 `key_pools.channel_id` 改为可空。
3. 将 `key_pools.channel_id` 的外键改为 `ON DELETE SET NULL`，禁止删除渠道级联删除号池。
4. 为 `channels.key_pool_id` 增加查询索引。

迁移只保留当前运行时已经生效的 `channels.key_pool_id`。已有 `key_pools.channel_id` 保留为默认/测试渠道提示，不会据此自动激活或改绑渠道。`Sync2` 只负责新模型结构，不替代显式生产迁移。

回滚迁移可以恢复非空和级联约束，但共享绑定仍由多个渠道字段表达；回滚前必须先清理 NULL 默认渠道并确认删除级联风险。

## 5. 管理接口

### 5.1 号池 CRUD

- `POST /admin/key-pools` 新请求只要求 `name`。
- 为兼容旧客户端，仍接受可选 `channel_id`；传入时在同一事务内创建号池并把该渠道绑定到新号池。
- 号池响应增加 `channel_ids`，按渠道 ID 升序返回全部绑定渠道。
- `GET /admin/key-pools?channel_id=...` 保持可用，改为通过 `channels.key_pool_id` 过滤。
- `GET /admin/key-pools/:id/channels` 继续返回全部绑定渠道。

### 5.2 批量绑定

新增或改造号池渠道绑定接口，使其接收完整的 `channel_ids` 集合。服务端在单个数据库事务中：

1. 校验号池和所有渠道存在。
2. 将所选渠道的 `key_pool_id` 更新为当前号池；渠道此前绑定其他号池时视为明确改绑。
3. 将此前绑定当前号池、但本次未选择的渠道更新为 `key_pool_id = 0`。
4. 清理所有受影响渠道的运行时缓存。

重复提交同一集合必须幂等。请求包含重复、零值或不存在的渠道 ID 时返回 `400`，不能部分保存。

### 5.3 删除

删除号池前检查是否仍有渠道引用：

- 有引用时返回 `409 Conflict`，列出或返回绑定渠道数量，要求先解绑。
- 无引用时在事务中删除池内 Key 和号池。

删除渠道只删除渠道自身，不影响号池或其他绑定渠道。

## 6. 运行时行为

普通 HTTP、SSE、Responses WebSocket、Realtime WebSocket、代理请求和异步任务继续读取已经选定渠道的 `key_pool_id`。现有池内 Sticky 分配、耗尽标记和 Key 轮转逻辑不变。

Sticky 分配键继续使用：

```text
pool_id + entity_id
```

因此同一用户或 API Key 通过不同渠道进入同一个共享号池时，会复用同一个上游 Key。这是共享号池的预期语义。渠道路由、模型组授权、计费、退款和日志仍使用实际命中的渠道 ID，不改为号池归属。

## 7. 供应商上传

供应商提交 Key 的兼容规则：

- 只传 `channel_id`：读取该渠道的 `key_pool_id`；未绑定时拒绝。
- 同时传 `pool_id` 和 `channel_id`：要求该渠道当前绑定该号池，否则拒绝。
- 只传 `pool_id`：要求号池允许供应商提交，并选取 ID 最小的启用绑定渠道执行 Key 有效性测试。
- 号池没有启用的绑定渠道时不能测试 Key，返回明确业务错误。

Key 写入、去重、审核状态和 `base_url_override` 行为保持不变。测试请求始终使用最终选定渠道的协议、认证方式和请求配置。

## 8. 管理页面

号池页面：

- 创建号池时不再强制选择渠道。
- 列表展示绑定渠道名称或绑定数量，不再展示单一 `channel_id` 归属。
- 绑定操作使用渠道多选控件，并明确提示选择已绑定其他号池的渠道会执行改绑。

渠道页面：

- 每个渠道仍使用单选控件选择一个号池。
- 号池候选不再按旧 `pool.channel_id` 过滤，所有有效号池均可选择。

## 9. 错误和一致性

- 所有绑定变更必须使用数据库事务。
- 不允许管理端响应成功但只更新部分渠道。
- 删除保护以数据库当前引用为准，不能依赖前端状态。
- 绑定完成后必须失效相关渠道缓存；池内 Sticky 状态不因新增共享渠道而清空。
- 号池停用时，所有引用该池的渠道按现有“号池不可用”行为失败，不自动退回渠道静态 Key。

## 10. 测试与验收

后端至少覆盖：

- 两个渠道可绑定同一号池并取得同一池内 Key。
- 一个渠道改绑新号池后不再引用旧号池。
- 批量绑定的新增、移除、改绑和幂等行为。
- 非法渠道集合不会部分写入。
- 被引用号池不能删除，解绑后可以删除。
- 删除一个渠道不会删除共享号池或影响另一渠道。
- 号池列表按 `channel_id` 正确反查。
- 供应商三种参数组合及无绑定渠道错误。
- HTTP/SSE、Responses WS、Realtime WS 和异步任务继续按渠道的 `key_pool_id` 工作。

前端至少覆盖：

- 创建独立号池无需渠道。
- 号池多选绑定并展示多个渠道。
- 渠道编辑器可选择任意号池。
- 删除受引用号池时展示后端冲突信息。

验证命令包括聚焦 Go 测试、`go test ./... -count=1`、前端单元测试和构建、`git diff --check`。真实 PostgreSQL 迁移演练必须单独记录；未配置测试数据库时不能声称已完成 PostgreSQL 验收。

## 11. 跨仓库一致性

OctoAPI 和 FanAPI 使用相同业务语义、接口字段和错误规则。两边分别提交迁移和测试，不通过复制数据库状态实现同步。发布时先执行数据库备份和迁移，再部署对应应用；任一仓库未完成迁移验证时，不发布该仓库的应用变更。
