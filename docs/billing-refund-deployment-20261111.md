# Durable refunds and historical recovery — v1.0.87

Redis INCRBY refund timeouts could execute repeatedly while the caller returned zero refunded credits, leaving no refund ledger or retry job. User 247's request 1815321 held 18,198 credits, owed 16,354 back, and left an unbacked 49,062 Redis quota. The exact number of Redis executions cannot be proved from the application log alone. The resulting quota/lease mismatch caused 276 pre-upstream failures, none of which created a consumption transaction.

Refunds now persist an intent before crediting money. The account balance, model credit, ledger, invitation attribution and vendor follow-up commit in one database transaction. Stable request/phase keys prevent duplicate partial refunds. New pending_db/running_db states prevent old workers from consuming new intents with legacy semantics. Database retries and ambiguous commits replay the same unique ledger key. Redis only receives best-effort cache invalidation. A typed quota-lease shortfall invalidates the stale quota instead of restoring it indefinitely; cache version remains 2 for rolling compatibility.

## Recovery

Audited all retained main-container logs from November 6 onward (about 420 MB), historical unsuccessful/pending requests, and recent successful requests missing settlement metadata. Confirmed and refunded 30 requests belonging to 9 users, totaling 9,233,663 credits, including 16,354 for user 247. Each original request now has exactly one recovery refund; all 30 jobs are done, and each request's net charge equals its reviewed original charge minus the recovery amount. The CLI dry run after application recognizes every entry as already refunded.

The private plan and evidence remain under /root/fanapi-billing-refund-v1.0.87/ and the task's private local audit directory. recovery-review.json records the plan hash. Sixteen full refunds restore original recorded upstream cost; fourteen partial refunds restore the exact user credit amount but use zero upstream cost correction because historical actual upstream costs cannot be reconstructed safely.

120 historical records remain unrefunded because their outcome is not established: 90 old pending requests, 29 manually marked unknown results, and one old streaming cancellation without stored usage. They are not asserted to be additional missing refunds. A legacy pending refund job for nonexistent test user 9999 has neither a charge nor a request record and was not credited. These exceptions are recorded separately in the private audit.
